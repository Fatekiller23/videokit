# VideoKit

B 站视频的探测、下载与转文稿。给一个链接，先告诉你有多少讲、哪些有字幕、有哪些清晰度可选，再按你的选择把视频或音频下下来。

有字幕的讲次直接产出交付文稿，无字幕的讲次自动走本地语音识别补齐，**一条命令跑完，不需要另跑一条**。两种来源落成同一个 `PartTranscript` 结构，只有 `source` 字段不同。

## 它解决什么

一门课几十讲、几十小时，逐集点开看有哪些字幕不现实。而这个信息决定后面要花多少算力：有字幕的讲次直接取，零成本；没有的才需要跑语音识别。

同一门课里两种状态会混着出现。实测 `BV1Y5QgB5Eas`（徐高 2025 年宏观课，30 讲），21 讲有字幕、9 讲没有，且与讲次时长无相关性。所以必须逐讲判定，不能按整条视频二选一。

## 七个入口

```
probe(url, cookies=None) -> Video
    探测。不下载任何文件数据。

part_subtitles(url, part, language="ai-zh", cookies=None) -> list[Segment]
    取回并解析某一讲的平台字幕轨。无字幕轨时抛 SubtitleUnavailable。

transcript_text(segments) -> str
    把分段拼成交付文稿的连续正文。分隔规则见「交付文稿」。

transcripts(url, out_dir, parts=None, cookies=None, audio_dir=None, engine=None, device="cpu") -> tuple[PartTranscript, ...]
    一条命令跑完。逐讲判定，有字幕的取其字幕，无字幕的取音频跑语音识别，
    两者都落成交付文件，只有 source 字段不同。

transcribe(wav, engine=None, device="cpu") -> list[Segment]
    把一讲的 16 kHz 单声道 WAV 转成带时间戳的分段。缺 ASR 依赖时抛
    TranscriptionUnavailable。

download_video(url, out_dir, parts=None, quality="720p", cookies=None) -> list[Path]
    下视频。自动合并分开的音视频流。

download_audio(url, out_dir, parts=None, cookies=None) -> list[Path]
    只下音轨，已是语音识别需要的 16 kHz 单声道 WAV。
```

`parts` 是按序号选讲次，省略表示全部。

`cookies` 一般不用传。登录过一次之后入口自己找到凭据，见下面「登录态」。

## 命令行

四个能力都能从命令行触发，不必 import 本模块。规格 user story 19 要的就是这个，接进工作台的人只需要一个入口。

```
uv run --python 3.12 python videokit.py probe      BV1Y5QgB5Eas
uv run --python 3.12 python videokit.py video     BV1Y5QgB5Eas --quality 720p --parts 3,4 --out videos
uv run --python 3.12 python videokit.py audio      BV1Y5QgB5Eas --out audio
uv run --python 3.12 python videokit.py transcript BV1Y5QgB5Eas --out transcripts
uv run --python 3.12 python videokit.py login
```

`--help` 打印全部子命令，`<子命令> --help` 打印那一条的用法并把其余子命令也列出来。参数名与帮助文本按「不读源码也能用」写。

| 选项 | 作用 |
|---|---|
| `--parts 3,4` | 只处理这几讲，省略表示全部 |
| `--out 目录` | 产物落点，省略分别是 `video/`、`audio/`、`transcripts/` |
| `--audio-out 目录` | 仅 `transcript`，音频落点 |
| `--quality 720p` | 仅 `video`，可选 `360p` / `480p` / `720p` / `1080p`，默认 `720p` |

**`--quality` 的名字由一张表统一驱动**，`_QUALITIES`。探测报告列出的档位、命令行的合法取值、`_format_selector` 认的键都来自它，所以给得出的名字一定下得动，报了未知档位时也会把合法名字列出来。

### 退出码

| 情况 | 退出码 |
|---|---|
| 全部成功，或全部跳过 | 0 |
| 有任何一讲 `failed` | 1 |
| 参数错、未知子命令 | 2 |
| 登录失效、视频取不到一类故障 | 1 |

`probe` 与两个下载共用的默认是 0 与非零。`transcript` 的判据见「交付文稿」一节，那里写了为什么它是这样而不是 #18 原本的退 0。

### 进度是真实的，不报百分比

下载按讲调用，每讲下完打印一行 `[n/总数]`。这样每次多花约 2.6 秒取信息开销（实测），换来整段可见。**不打印百分比**，因为库只报 yt-dlp 写完哪些文件，那是唯一量得出来的进度，多报就是编数字。

转写通过包住 engine 实现，每讲开始与结束各一行并报耗时，模型加载单独一行并报加载耗时。**走的是 stderr**，所以 stdout 重定向到文件仍然拿到交付报告，终端上还能看到进展。一次全量约 48 分钟，长时间无输出会被当成卡死。

用包装 engine 而不是给 `transcripts` 加进度参数，是因为 `transcripts` 拥有逐讲判定、失败记录与跳过预检，命令行必须调它而不是自己再写一遍循环；#18 与 #19 同时在改它的接口。包 engine 观测的是一条已经存在的边界，也是贵的那条。

### 会员高清档是否拿到

**这一项只能看 yt-dlp 打印的那句话，格式表里看不出来。**

实测同一视频「有效凭据」与「完全不带凭据」两次 `--dump-single-json`，`formats` 表逐条完全相同，15 行，`format_id` / `quality` / `format` / `tbr` 全同，最高 `quality` 都是 80。所以读 `formats` 的程序会把普通 1080P 当成高码率档报出去。

那句话的措辞实测是

```
[BiliBili] Format(s) 1080P 高码率 are missing; you have to become a premium member to download them.
```

**它落在 stdout，不是 stderr。** 这是本机实测，与早先的勘察记录相反。

| 调用 | premium 行在 stdout | stderr |
|---|---|---|
| `--list-subs`，有效凭据 | 30 行 | 0 字节 |
| `--list-subs`，无凭据 | 30 行 | 5103 字节，全是登录告警 |

勘察记录里的 stderr 副本属于无凭据那次运行，那里 stderr 装的是登录告警。`missing_tiers` 因此两个流都扫。

**措辞也不随登录态变。** 实测两次都只列 `1080P 高码率` 一个档。缺哪个会员档仍然判断不了，能判断的只是「有档被扣下了」，以及被扣下的是不是高码率那档。

`premium_unavailable` 认的是 `高码率` 这个标记词而不是整句，因为同页的普通档叫 `1080P 高清`，两者只差这个词。

### 控制台编码

控制台是 cp936，`sys.stdout.encoding` 是 gbk。实测 U+20000、emoji、U+2022、U+FFFD 写入时会抛 `UnicodeEncodeError`，普通汉字与报告用的制表符正常。

讲次标题来自平台，不能假定可编码，所以 `main` 把自己的两个流包一层替换降级，实测真管道上不再抛栈。**不改 `sys.stdout`，也不设 `PYTHONIOENCODING`**，因为 `_run` 让平台决定子进程编码是有意的，那条语义有测试锁着，而设这个变量会把中文标题全变成替换字符，见「已知限制」。

### 为什么探测要单独一个入口

「先看看有什么再决定下什么」是真实用法。并进下载里，调用方就无法只问不取。

### 为什么音频要单独一个入口

同一讲，视频 130 MB 到 340 MB，音频 40 MB 左右，差一个数量级。只做文稿时不需要视频。

### 为什么字幕要单独一个入口

有字幕的讲次不需要跑语音识别，零成本。所以「这一讲走字幕还是走 ASR」是逐讲的决策，输入就是这次调用的结果。实测 `BV1Y5QgB5Eas` 有字幕的 21 讲与无字幕的 9 讲时长分布无差别，所以这个判断不能按整条视频做。

## 平台字幕

```
part_subtitles(url, part, language="ai-zh", cookies=None) -> list[Segment]
```

返回按起始时间有序的 `Segment` 列表，每个 `Segment` 有自己的 `start_sec`、`end_sec` 与 `text`。

```python
for segment in videokit.part_subtitles(url, part=12):
    print(segment.start_sec, segment.text)
```

`text` 不含时间戳。两条来源的时间戳粒度不同（平台字幕逐句，语音识别可到词级），混在字符串里下游没法统一处理。

`language` 默认 `ai-zh`，是这些视频唯一的机器生成中文轨。

### 「取不到字幕轨」与「解析出空列表」是两回事

这两种结果的处置方式完全不同，所以用异常分开。

- 取不到字幕轨，或该语言的轨不存在，或轨里没有合法时间块，**抛 `SubtitleUnavailable`**。这一讲的正确处置是转去跑语音识别，而不是产出一份空文稿。
- `parse_srt("")` 返回空列表。这是纯函数对空输入的回应。

异常里带讲次号，调用方能直接指出是哪一讲。

「解析出 0 段」只可能来自空输入，实测 21 份真实录制件没有一份解析出 0 段。

### 无标点是已接受的取舍

**`ai-zh` 字幕完全没有句读，这是一条实测事实，不是识别缺陷，也不是本包要修的问题。**

实测 21 份真实字幕轨，共 454245 个正文字符。

| 项 | 实测值 |
|---|---|
| 中文全角标点（，。、？！等） | 0 |
| ASCII `,` `?` `!` `;` | 0 |
| 分段首尾带空格 | 0 |
| 分段以句末标点结尾 | 0 |

文本会是一整条没有句号的连续流。使用者已接受这个结果，与「字幕直接用、不做来源标记」是同一条决策的两面。补救路径是把平台字幕也过一遍标点恢复，代价是会重算原有时间戳，不在本包范围内。

配套的两条实测事实，写在这里以免后来者当成解析 bug。

- **相邻重复分段保留，不去重。** 实测 21 份里 17 对相邻分段正文完全相同，例如 p12 第 418 与 419 段都是 `也不可能啊`。这是两个不同时段的真实内容，删掉任一段会丢一秒左右的话。`parse_srt` 因此不做事后去重。
- **小数点后的浮点泄漏原样保留。** 例如 `但中国是1.31000.30000美元了`（p03 第 2101 段）、`33.4000000000000`（p21 第 742 段）。这是 B 站自己的 ASR 流水线把 Python `float` 的 repr 写进了字幕，属于上游数据，本包不修。

### 字幕文本从 stdout 读，不从文件读

`yt-dlp` 会把字幕写成文件，而文件名本包推不出来。实测两条。

- `-o` 的占位符管不到字幕文件名，写出来的是 `BV1Y5QgB5Eas_p12.ai-zh.srt`。
- `--print after_move:filepath` 对字幕返回空，而下载视频时它是有输出的。

所以改用 `--print "%(requested_subtitles)j"`，字幕文本本身就在这个 JSON 里。**实测这份文本与 `yt-dlp` 写出的文件逐字节相同**，p12 两边 sha256 都是 `b13447822d78f2a02fe39101a66c5b17283602fdeca82c96725e0557f224c24c`，123777 字节。同时因为 `--print` 自带 `--simulate` 语义，磁盘上不会落文件，也就没有文件名编码问题。

这个载荷是纯 ASCII 的，中文被转义成 `\uXXXX`。这一点在本包里很重要，`_run` 有意按控制台代码页解码子进程输出，转义载荷不受影响。

## 交付文稿

一条命令，给一个 BV 号，逐讲判定并产出所有有字幕讲次的纯文本文稿。

```
uv run --python 3.12 python videokit.py transcript BV1Y5QgB5Eas --out transcripts
uv run --python 3.12 python videokit.py transcript https://www.bilibili.com/video/BV1Y5QgB5Eas --parts 3,4
```

从 Python 里调用是同一件事。

```python
records = videokit.transcripts("BV1Y5QgB5Eas", Path("transcripts"))
```

`parts` 是 `--parts` / 列表，省略表示全部讲次。`out_dir` / `--out` 省略时落在当前目录的 `transcripts/`，`audio_dir` / `--audio-out` 省略时落在当前目录的 `audio/`。

**两条路径在这一个调用里合流。** 有字幕的讲次取字幕即可；无字幕的讲次自动取 16 kHz 单声道音频并跑语音识别，不需要另跑一条命令、不需要先看报告再决定。`source` 是唯一区分两者的字段，`"platform"` 与 `"asr"`。

跑真实的 `BV1Y5QgB5Eas`，两条路径分别是 21 讲与 9 讲，实测一次约 45 分钟，其中语音识别部分约 39 分钟。

交付文件名带讲次序号与标题，所以目录列表按课程顺序读。

```
03-【徐高2025年宏观课】中国宏观经济 p03 02-宏观经济数据和宏观逻辑的逻辑-1.txt
```

命令结尾的汇总按来源分列，并点名哪些讲次来自 ASR。没有这一行，一门课的文稿里有几分钟是机器听写的、几分钟是平台字幕抄的，读的人看不出来。

**退出码回答「每一讲是否都产出了文稿」。有任何一讲 `failed` 就非零，全部成功或全部跳过则 0。**

判据读的是 `records` 里的 `status`，不是把判定重算一遍。

早先这里写的是「一讲失败时仍然退出 0」，理由是整批跑完了。**已按裁决改掉，理由是这个命令的调用方是别的程序。** 工作台拿到的是进程退出码，拿不到本模块的 `records`，所以 `videokit transcript BVxxx && echo 完成` 会在每一讲都失败的一次运行里照样打印「完成」。汇总文本是给人看的，让脚本去解析它判断成败不合理。

两件事因此分开。退出码是给机器的答案，汇总行是给人的答案，两者不必对「跑完了」取同一个意思。失败讲次在汇总行里点名并说明该不该重试，那部分不变。

### `source` 只服务程序，不进交付文稿

**这一条必须写清楚，否则后来者会认为规格自相矛盾。**

使用者已定「字幕直接用，不做来源标记，不做质量分级」，规格 Out of Scope 里也写了「交付文稿不做来源区分，不做质量打分」。而中间产物 `PartTranscript` 有 `source` 字段。两处并不冲突，因为它们说的是两层不同的东西。

- **中间产物是给程序的。** 它要区分这一讲的正文从哪来，因为两条来源的时间戳粒度不同（平台字幕逐句，语音识别可到词级），标点风格也不同。代码里用得上，所以要留着。
- **交付文稿是给读者的。** 读者要的是能读的正文，来源标记与质量分级对他只是噪声，所以一律不写。

所以 `write_transcript` 只写 `transcript_text(record.segments)` 的结果，`source`、`language`、`status`、`failure_reason` 与任何时间戳都不进文件。测试 `DeliverableFiles.test_the_source_does_not_reach_the_file` 锁着这条。

### 逐讲判定，不按整条视频二选一

实测 `BV1Y5QgB5Eas` 21 讲有字幕、9 讲没有，且缺失的讲次夹在中间，第 1、2 讲就没有。所以判定逐讲做，且**无字幕的讲次不自动跳过，也不中止整批，而是当场用语音识别补齐**。

判定写在 `part_transcript`，两条分支产出同一种记录。

| 讲次状态 | 走的路径 | `source` | `language` |
|---|---|---|---|
| 有字幕轨 | `part_subtitles` | `"platform"` | 探到的轨语言，实测总是 `"ai-zh"` |
| 无字幕轨 | `part_audio` 取音频，再 `transcribe` | `"asr"` | `"zh"` |

**除了 `source` 与 `language`，两个记录的每个字段都以同样方式填。** 所以下游拿到一个 `PartTranscript` 时不需要问它从哪来，`write_transcript` 也不问。这是本票要的合流，也是「不需要另跑一条命令」的实现。

**`status` 有 `ok`、`skipped`、`failed` 三个取值。** #17 曾经有个第四值 `pending`，表示「这一讲有讲次但音频还没取」。两个结果现在都在同一趟里定下来，`pending` 已删除。没有任何代码路径能产出的取值留着，只会让调用方去处理一个不可能发生的分支。

`skipped` 是产物层那一半，#19 加的。判定在读这一讲之前做，命中就直接进下一条循环，`part_transcript` 都不进。详见「持久化」。

**一讲失败不中止整批，也不写文件。** 走 ASR 的讲次抛错时记成 `failed`，`failure_reason` 为 `asr_error`，批次继续。已经写完的讲次不受影响，每一讲是完成即写，没有回退。

**引擎在一批里只加载一次。** 实测加载 29 到 50 秒，47 分钟的一讲转写约 200 秒。逐讲重加载会给一批 30 讲加上约 20 分钟。做法是 `_DeferredEngine`，第一次真正用到时才建，之后复用；调用方自己持有引擎时从 `engine=` 传进来，`_DeferredEngine` 就不参与。**整批都不需要语音识别时，一次加载都不发生。**

**音频文件已在磁盘上就不重下。** 9 讲音频合计约 1.1 GB，重跑时重下这一段是纯浪费。

### 平台字幕无标点，这一条落在交付文稿里

交付文稿会包含一整条没有句号的连续流（平台那 21 讲）和带标点的段落（ASR 那 9 讲），**段落划分只能靠 ASR 那一半的标点，本包不额外加策略**。这是两条上游数据本来的样子，见「无标点是已接受的取舍」。

**同一门课因此会混着两种风格，这是已接受的取舍，不是缺陷。** 平台 `ai-zh` 轨的标点数为零（实测 21 份共 454245 字，CJK 句读与 ASCII `, ? ! ;` 全为 0），而 `ct-punc` 给 ASR 文本加了标点。同一门课的文稿里读起来会有明显差异，这是实测结果，不是渲染问题。

**补救路径记在这里，本期不做。** 把平台字幕也过一遍标点恢复，两条路径的风格就能统一。代价是这会重算已有的时间戳，而那批时间戳本身是对的，所以收益不足以抵掉重算的风险。要做就单独一票。

### 不做简繁转换

**两条路径都按引擎与平台给出的简体原样交付，本包不做任何简繁转换。** 若将来需要，正确的包名是 **`opencc`**。

**这个命名陷阱必须记住。** PyPI 上有多个名字相近的包，其中 `opencc-python-reimplemented` 之类的实现把「头发」转成「頭發」，因为它是逐字转换而不是按词转换。`opencc` 做的是词级转换，同一句话能正确得到「頭髮」。装错包不会报错，只会安静地给出错误的字。

```text
正确：  opencc        词级转换，「头发」→「頭髮」
错误：  同名近似的包   逐字转换，「头发」→「頭發」
```

### 拼接规则是量出来的，不是选的

**朴素 `"".join` 会把 55 个位置的词粘在一起，`" ".join` 会插入 38994 个原文没有的空格。** 两个都不能用。

实测 21 份真实字幕轨，共 40283 个分段、40262 个相邻边界，按两侧字符分类。

| 前段末 | 后段首 | 个数 | 分隔符 |
|---|---|---|---|
| 汉字 | 汉字 | 38994 | 无 |
| 汉字 | ASCII 字母数字 | 572 | 无 |
| ASCII 字母数字 | 汉字 | 324 | 无 |
| 标点或符号 | 汉字 | 294 | 无 |
| **ASCII 字母数字** | **ASCII 字母数字** | **55** | **一个半角空格** |
| 标点或符号 | ASCII 字母数字 | 23 | 无 |

规则因此是**两侧都是 ASCII 字母数字时插入一个半角空格，其余零分隔符**。55 处的真实例子。

| 前段尾部 | 后段头部 | 不插空格的后果 |
|---|---|---|
| `然后呢回答就very good` | `Good` | `very goodGood` |
| `60616263646566676869` | `70707172737475767778` | 两串数字连成 39 位 |

反面例子也要记。`农业占比7%` 后面接 `然后呢这个第二就是第一产`，`%` 不是字母数字，所以不插空格，拼出来读着正常。这类分段有 315 个。

这条规则写在 `_needs_separator`，改动它就要把这四个数字重新量一遍。

### 不去重，也不修上游的浮点泄漏

相邻重复分段 17 对原样保留，例如 p12 第 418 与 419 段都是 `也不可能啊`，交付文稿里读作 `...政治阻力极大啊也不可能啊也不可能啊`。它们是两段不同时段的真实内容，删掉任一段会丢一秒左右的话。

`大概只有三十六三十六.8000000000000` 这类浮点泄漏也原样进入文稿。那是 B 站自己的 ASR 流水线把 `float` 的 `repr` 写进了字幕，属于上游数据。

### 交付文稿不含时间戳

`Segment` 的 `start_sec` / `end_sec` 是独立字段，`transcript_text` 只用 `text`。测试同时断言交付内容里没有 `-->`、没有 `HH:MM:SS`、也没有秒数的小数写法。

## 语音识别

```
transcribe(wav, engine=None, device="cpu") -> list[Segment]
```

输入是一讲的 16 kHz 单声道 WAV，就是 `download_audio` 落下来的那个文件。输出是与平台字幕路径同一个 `Segment` 结构，带 `start_sec`、`end_sec` 和正文。

引擎是 `paraformer-zh` + `fsmn-vad` + `ct-punc`，全部是必需项，见 `engine_kwargs`。

**`ct-punc` 不是可选优化。** 实测关掉它后输出变成逐字之间带空格，3023 个字符里 1511 个空格，零标点。它同时负责把逐字标记拼回连续文本。没有标点就没有可分段的位置，这条链路上游就没有产物。

**模型一次加载、反复使用。** 加载 29 到 50 秒，是每讲都要付的成本，所以引擎从 `engine=` 传进来。跑 30 讲时加载一次，不要每讲重来。

**CPU 够用。** 实测 47.5 分钟音频约 209 秒，13.7 倍实时。不必为 GPU 做额外适配。

### 时间戳配对规则

`result["timestamp"]` 是毫秒对的列表，但**它的长度不等于文本长度**。实测一讲 52.7 分钟的完整运行，`len(text)` 是 17123，`len(timestamp)` 是 15908。

规则是**一个汉字，或一整段连续的 ASCII 字母数字，消耗一对毫秒。标点与空白不消耗。**

实测算术。15883 个汉字加 25 段 ASCII 连续串等于 15908，与 `len(timestamp)` 精确相等。反证也干净，按「每字符一对」假设会多出 61 对，正好等于 25 段 ASCII 串内部多算的字母数（`GDP` 23 次、`WTO` 9 次等）。

所以配对不能按字符下标做。`recognised_units` 用一条正则切出单元，`asr_segments` 按单元下标取时间。

**两个数不相等时抛 `AsrError`，不猜。** 错配之后任何一种配对都能产出看着像样的文稿，这正是要拒绝的失败模式。

### 分段边界是标点

`text` 里每出现一个标点就断一段。实现是扫文本找标点，**不读 `sentence_info`**。

理由是 `sentence_info` 的文本在长音频上是错的。FunASR 1.4.16 里 `ct-punc` 的分词把 15088 个空格词展开成 15908 个标点 id，而句子拼接函数用 `text_postprocessed.split()` 去配这 15908 个 id，两边对不上。实测完整运行上从第 318 个字符起文本归属错位，拼接后 17165 字符对不上真实的 17123。**它的 `start` 与 `end` 毫秒是对的，文本不是。** 自算规则与它的 1152 段毫秒边界逐段相等，0 处不同，所以自己断没有损失。

**分界标点必须包含 `.` 与 `,`。** 它们是 `ct-punc` 给 ASCII 词加的西文标点。实测只用 `，。？！、` 得到 1148 段，加上这两个得到 1152 段，与 `sentence_info` 精确相等。

### 设备校验

**必须读实际设备，不能信传进去的参数。** 实测把 `device="cuda:0"` 传给一台 `torch.cuda.is_available()` 为 `False` 的机器，FunASR 静默降级到 CPU，不报错不警告，转写结果完全正常。

读法是 `next(model.model.parameters()).device`。三个看起来能用的属性都不可用。

| 属性 | 实际情况 |
|---|---|
| `model.device` | 抛 `AttributeError`，不存在 |
| `model.model.device` | 返回 `None`，**看着像「没有设备信息」，是假象** |
| `next(model.model.parameters()).device` | 正确，用这个 |

`verify_device(model, requested)` 在设备不符时抛 `AsrError`，`transcribe` 在读音频之前就调用它，所以降级会在启动时报出来，而不是几分钟工作量之后。

### 口语填充词保留，是有意的

**「啊」「呢」「就是」「这个」全部保留，不做清理。这不是识别缺陷，是本包的有意取舍，不要当 bug 修。**

实测一讲 52.7 分钟的完整运行里，「啊」出现 277 次、「这个」424 次、「就是」60 次、「呃」89 次，全部留在文本里。

理由是文稿的用途是让人读这门课讲了什么，而填充词是讲课风格的一部分。清掉它们会让不同讲次的文风看起来比实际更整齐，也会让引用原文时对不上音频。同一门课的平台字幕路径同样保留填充词，两条路径在这一点上一致。

清理若要加，应该是显式的后处理步骤、带自己的开关，而不是藏在转写里的默认行为。

## 登录态

B 站字幕未登录拿不到，所以要先登录一次。取凭据由程序引导，不需要手工导出 Cookie 文件。

```
uv run --python 3.12 python videokit.py login
```

这条命令拉起浏览器窗口，扫一次码，然后把凭据落盘并打印它的路径。之后 `probe` 与两个 `download_*` 自动使用它。

从 Python 里调用是同一件事。

```python
videokit.login()             # 拉起浏览器，扫码一次，落盘凭据
videokit.reuse_or_login()    # 已有凭据就复用，没有才拉起浏览器
```

显式传 `cookies=` 仍然生效，优先级高于默认发现。

命令行入口见下面「命令行」一节。`login` 能在不 import 本模块的前提下跑起来，这正是命令行存在的理由。

### 登录态失效时被识别出来

`probe` 在没拿到字幕轨、且 yt-dlp 报出登录告警时抛 `LoginRequired`，而不是返回一份每讲都空的 `Video`。提示指向 `videokit.py login`，不贴 yt-dlp 的原始告警。

判定用两个信号，缺一不可。

- 整条视频里有任何一讲返回真实字幕轨，登录态就算有效。
- 一讲都没有，**且** stderr 出现 `Subtitles are only available when logged in`，判为登录态缺失。
- 一讲都没有，**且**没有该告警，判为该视频确实没有字幕，正常返回。

**不能只看「字幕轨为空」。** 实测有效凭据下 `BV1Y5QgB5Eas` 的 p1 本就无字幕，返回的表同样是空的，与未登录的表现逐字节同形。那行告警是唯一能区分两者的信号。同理，**退出码完全无用**，六种实测输入退出码全是 0。

**也不断言是「过期」。** 「过期」与「从未登录」在外部表现上完全一致，文案统一说需要登录并给出入口，不猜原因。

**这条与交付文稿路径的关系要说清。** `transcripts` 会把这个异常往上抛，整批就停在那里，不会把 30 讲都记成待 ASR。原因很直接：登录失效时每一讲都表现为无字幕轨，若照单记成「待 ASR」，使用者会拿一门课的 ASR 时间去补一个只要重新导出凭据就能解决的问题。反过来，`SubtitleUnavailable` 只表示这一讲没有字幕轨，那才是待 ASR。

告警走 stderr 而退出码是 0，所以 `_run` 返回 `RunOutput(stdout, stderr)` 两个流，不再只返回 stdout。

`part_subtitles` 用同一条判定。取不到轨道且出现告警时抛 `LoginRequired`，否则才抛 `SubtitleUnavailable`。两者都在 stdout 上没有内容，但补救动作相反，一个去重新登录，一个转语音识别。

### 为什么必须走 CDP 导出

程序无法直接读浏览器的 Cookie 库。本机实测四种方式全部失败，记录在 `docs/research/measured-bilibili-subtitle-availability.md`。

| 方式 | 结果 |
|---|---|
| `yt-dlp --cookies-from-browser chrome` | `Could not copy Chrome cookie database`，数据库被进程锁住 |
| `yt-dlp --cookies-from-browser edge` | `Failed to decrypt with DPAPI`，新版 Chromium app-bound 加密 |
| `chrome-agent --copy-cookies` | `Chrome cookies file not found`，它查旧路径 `Default\Cookies`，实际在 `Default\Network\Cookies` |
| robocopy 备份语义复制 | 退出码 16，文件锁未绕过 |

所以路径是：程序拉起一个带远程调试端口的 Chrome，用户在其中扫码，程序通过 CDP 取 Cookie 落盘。

### 两个必须的 CDP 细节

漏掉任何一个都不报错，只是拿到 0 条 Cookie。这与「登录态过期」表现完全一样，所以没有测试覆盖就会静默失败。

- **必须附着到 bilibili 的 page target，且先发 `Network.enable`。** 附着到浏览器级 WebSocket 直接问，返回 0 条。
- **Chrome 启动必须带 `--remote-allow-origins=*`。** Chrome 111 起默认拒绝带 Origin 头的 CDP 连接，报 403，看起来像网络问题而不是缺参数。

这两条都落在 `videokit.chrome_argv` 与 `videokit.cdp_cookies`，测试直接对着断言。

### 凭据文件的位置与权限

凭据落在仓库之外的数据目录，默认 `%LOCALAPPDATA%\VideoKit\cookies.txt`。落盘时降权到只有当前账户可读写，文件与它所在的目录都降。

**放进仓库是不允许的，这一条编码成结构而不是靠记忆。** 两道独立的防线：

- 路径在仓库工作区之外，就地放进仓库这个错误本身不可用。
- `.gitignore` 里有 `cookies.txt`、`*cookies*.txt` 与 `browser-profile/`，万一有人手工把数据目录复制进来，`git check-ignore` 仍然拦住。

第三条容易漏。**浏览器 profile 与凭据文件同级敏感**，它带着同一个登录态，只挡 `cookies.txt` 会漏掉 profile 这一半。断言因此同时查目录本身与目录里的 Cookie 库文件。

`VIDEOKIT_DATA_DIR` 可覆盖数据目录，测试靠它保持隔离。

### profile 复用

浏览器 profile 落在数据目录下的 `browser-profile`。登录态跟着 profile 走，重启浏览器后仍然有效，所以扫码是一次性的。

### 导出失败时报的是哪一步

`LoginError` 的文案指出失败的环节，四种情况分开。

- 找不到 `chrome.exe`，报查过的路径。
- 远程调试端口连不上，报 URL 与原因。
- 没有 page target 可附着，报 Chrome 报了几个 target。
- Cookie 拿到了但没有 `SESSDATA`，报用户需要扫码。

最后一种最需要区分。匿名 profile 也会返回一堆 Cookie，只看「拿到的 Cookie 是否非空」会把未登录判成已登录。

## 数据结构

```
Part
  index           讲次序号，从 1 起
  id              平台标识，如 BV1Y5QgB5Eas_p3
  title           讲次标题
  duration_sec    秒
  subtitle_langs  字幕语言元组，空表示没有字幕

Video
  id, title
  parts           Part 元组，按 index 排序
  formats         yt-dlp 的原始格式表

Segment
  start_sec       分段起始秒，浮点
  end_sec         分段结束秒，浮点
  text            该段正文，不含时间戳

PartTranscript
  bvid            如 BV1Y5QgB5Eas
  index           讲次序号，从 1 起
  title           讲次标题
  duration_sec    秒
  source          "platform" | "asr" | None。中间产物用，不进交付文稿
  language        "ai-zh" | "zh" | None
  segments        Segment 元组
  status          "ok" | "skipped" | "failed"
  failure_reason  None | "no_audio" | "asr_error"

RecognisedUnit
  start           单元在正文里的起始字符下标
  end             结束下标
  text            该单元文字，一个汉字或一段 ASCII 字母数字
```

`source` 与交付文稿的分层见「`source` 只服务程序，不进交付文稿」。

`status` 与 `failure_reason` 分开，因为失败原因决定重跑策略。**`no_audio` 重试多少次都不会成功，`asr_error` 可以重试。** 混成一个字段，调用方就无从判断该重试还是放弃。失败汇总把这条后果直接写出来，`failed: 2 (asr_error, retryable)`，读者不必回头查两个字符串的含义。

`status` 有 `ok`、`skipped`、`failed` 三个取值。`ok` 是本次跑出来的，`skipped` 是产物已在磁盘上、这次没做任何事的讲次，`failed` 是没产出文稿的讲次。`skipped` 是 #19 加的，详见「持久化」；`failed` 与 `failure_reason` 是 #18 的，详见下一段。

**本票的 `source` 只有两个取值，且两条路径都会产出 `ok` 记录。** `"platform"` 与 `"asr"` 的区别只剩来源，结构完全一致。`language` 随之分别是探到的轨语言与 `"zh"`。

`Part.has_subtitles` 是判断有没有字幕的入口，不要直接看 `subtitle_langs` 是否非空以外的条件。

`Segment.text` 在两条路径上标点情况不同。平台字幕不含标点是上游数据本来的样子，见「平台字幕」一节；ASR 分段含标点，且边界就在标点上。

## 持久化

**只有产物层持久化，探测结果每次都重新探。** 这是规格里唯一一处持久化。探测 30 讲的成本折算下来比引入状态管理更便宜，也没有缓存与实际脱节的失效问题。实测一次 30 讲全部命中的运行仍是 75.1 秒，其中两次 `yt-dlp` 探测调用、零次字幕取回、零次音频下载、零次引擎调用，所以这 75.1 秒就是探测加跳过的价钱。

**跳过判定读文件，不看文件名是否存在。** 交付文稿是连续 UTF-8 正文，没有结尾换行，也没有结束标记，所以被中断写坏的前缀与完整文件从外面看一模一样。判定用两条，都量过。

- **必须能按严格 UTF-8 解码。** 文稿是中文，三字节字符占多数，所以在任意字节位置截断通常会劈开一个字符。实测对 30 份真实产物取 11 个截断点，330 次里 223 次抛 `UnicodeDecodeError`。
- **正文长度要够。** 剩下 107 次截断恰好落在字符边界上，解得出来。实测 `23` 那道在 25591 字节处截断仍是 8537 个干净字符、读起来像一份文稿，所以只看解码会把它当成完成品，静默少掉 8586 个字。第二条用「每秒钟讲次时长对应多少字符」判，下限是 `_MIN_CHARS_PER_SEC = 3.0`。

**下限为何是 3.0 而不是实测最低的 4.239。** 30 份真实产物的密度区间是每秒 4.239（第 30 讲）到 5.418（第 23 讲），同一门课内部相差 1.28 倍，所以下限不能压着最低值设。两种错法代价不对称。设高了，已完成的讲次会被重跑，付出的是分钟；设低了，只会放过一个明显短的文件。3.0 对 30 份真实产物零误判，且拒绝实测的半截文件（2.701）。

**写入是先建后换，不是原地截断。** `Path.write_text` 以 `w` 模式打开目标，写第一个字节之前就把文件截成 0 字节。实测把一份 1500 字节的完成品重写到一个编码失败的载荷，文件被破坏成 0 字节；进程在写入中途被杀留下同样的东西。这正是跳过判定要去猜的那种文件，所以本模块不能自己造一个。现在载荷先编码，再写同目录的 `.partial` 临时文件，最后 `os.replace` 换名。中断只会留下旧产物或没有文件，不会留下像是交付品的碎片。临时文件是同目录的兄弟文件，不是系统临时目录，因为 `os.replace` 只在同一文件系统内原子。

**跳过的讲次不重新落文件，也不写入 `segments`。** 交付文件本身就是产物，跳过就是什么都不做，文件时间戳实测不变。跳过记录带 `status = "skipped"`，汇总里单独一行计数并列出讲次号，不计入本次交付数。一个跳过的讲次在「文稿存在」这层是 `ok`，但不记成 `ok`，否则会被算成本次跑出来的成果。

**实测的跳过与重跑对照，用 #17 那次真实运行的 30 份产物。**

| 场景 | 输入 | 耗时 | 字幕取回 | 音频下载 | 引擎加载 | 结果 |
|---|---|---|---|---|---|---|
| 全部跳过 | 30 份完整产物 | 75.1 秒 | 0 | 0 | 0 | 30 讲全 `skipped` |
| 全部跳过，合并后复验 | 30 份完整产物 | 73.5 秒 | 0 | 0 | 0 | 同上 |
| 两讲截断 | 第 3、23 讲截断，只选这两讲 | 375.7 秒 | 1 | 0 | 1 | 两讲都 `ok` |
| 混合，合入 #18 后 | 28 份完整、第 3 与 23 讲截断 | 336.8 秒 | 1 | 0 | 1 | 28 讲 `skipped`，2 讲 `ok` |
| 第 3 讲对照 | 完整产物 | 73.1 秒 | 0 | 0 | 0 | `skipped` |
| 第 3 讲对照 | 半截产物 | 76.6 秒 | 1 | 0 | 0 | `ok` |
| 第 23 讲对照 | 完整产物 | 74.2 秒 | 0 | 0 | 0 | `skipped` |
| 第 23 讲对照 | 半截产物 | 347.3 秒 | 0 | 0 | 1 | `ok` |

**第 3 讲的两次相差 3.5 秒，因为它是平台字幕讲次，固定成本是探测。** 单独探一次实测 72.5 秒，占了 73.1 秒里的绝大部分。所以「跳过比重新取字幕快多少」在平台字幕讲次上看不出来，省下的是取回字幕那段。第 23 讲是无字幕讲次，重跑要走完整的语音识别，`74.2 秒对 347.3 秒` 那一对才是跳过省下的大头，约 273 秒。

**重跑的产物与 #17 原产物逐字节相同。** 第 3 讲 75845 字节 sha256 `8bb41bd48d8fff06…`，第 23 讲 51185 字节 sha256 `d1f57fbeee2c9bdb…`，四轮实测都是这两个值。所以重跑不是「重新写了一份差不多」，是重建了同一份。

**混合那一轮是最强的一次验证。** 它是「补下缺失讲次」的真实形态。28 份完整产物的 `mtime` 全部不变，第 3、23 讲的字节数从 37920、25591 变回 75845、51185，两次探测调用、一次字幕取回、零次音频下载（音频本来就在磁盘上）。输出目录里没有 `.partial` 残留。

## 代码结构

`videokit.py` 是全部实现。分三层。

**`_run` 是唯一的网络边界。** 所有 `yt-dlp` 调用都从这里出去。它返回 `RunOutput(stdout, stderr)` 两个流，因为登录告警写在 stderr 而退出码是 0。**模型是第二个边界，在 `transcribe` 的 `engine=` 参数上。** 其余全是纯函数。

**`probe` 用两次 `yt-dlp` 调用，这是 B 站提取器的现状，不是设计偏好。**

- `--dump-single-json` 给出全部讲次的结构和格式表，**但字幕字段对 B 站返回空对象**，即使那一讲确实有字幕。
- `--list-subs` 能正确报出字幕，但只输出文本版，且会遍历每个讲次。

如果不清楚这一点，很容易想「优化成一次调用」，然后得到「所有视频都没字幕」的错误结论，接着给每一讲都跑一遍语音识别。相关上游问题见 [yt-dlp #17527](https://github.com/yt-dlp/yt-dlp/issues/17527)，未修。

**`parse_subtitle_table` 用正则解析文本块。** 三条规则：块起始、表头、语言行。实测三种输入形态（30 讲合集、5 讲视频、单视频）形状一致，同一套规则全部通过。

两种必须处理的边界：

- **讲次标识符有两种形态。** 合集是 `BV1Y5QgB5Eas_p3`，单视频是 `BV1GJ411x7h7` 没有后缀。规则不得假定后缀存在。
- **`danmaku` 必须排除。** 它是被无条件附加的弹幕 XML，与字幕无关。只含 `danmaku` 等价于没有字幕。漏掉这一条，所有视频都会被判成有字幕。

**`parse_srt` 解析字幕轨。** 结构是严格四行一块，`index / timestamp / text / blank`，全文件 `4N+1` 行，以一个空行收尾。实测 21 份共 40283 个分段，零例外。两条实现上的要求。

- **索引行不解析。** 有 10 个分段的正文本身就是纯数字（p18 第 366 到 370 段等），所以「整数行」和「索引行」从字面上分不开。改用时间行作锚点，而正文里 `-->` 出现 0 次，锚点不会误判。
- **按时间行的下一行取正文，不按空行切块。** 空行只做块分隔、不承载内容，跳过即可。这样也容忍被字节区间裁掉末行空行的字幕轨。

浮点秒由 `毫秒 / 1000` 得到，不加舍入。实测这个除法在真实取值上与原文本等值，例如 `835719 / 1000 == 835.719`。

**`_format_selector` 把清晰度名字映射到格式编号。** B 站不提供合流的流，选择器要同时指名一路视频和一路音频。

**转文稿这一层是纯函数加一个循环。** `_needs_separator` 与 `transcript_text` 是纯函数，吃 `Segment` 列表出字符串；`transcript_filename` 与 `write_transcript` 碰文件系统；`part_transcript` 判定一讲并合流两条来源；`transcripts` 遍历全部讲次并落文件。

`_preferred_language` 在 `ai-zh`、`zh-CN`、`zh` 里按序取第一个存在的。这 21 讲只有 `ai-zh`，但入口收的是 `Part.subtitle_langs`，不该假定只有一个。

`video_url` 把裸 BV 号补成 URL，两者都收，使用者不用自己拼前缀。

`part_audio` 取一讲的音频，已在磁盘上就直接返回，不再调 `yt-dlp`。`audio_path` 是找文件的规则，`AUDIO_TEMPLATE` 是 `download_audio` 的命名模板；两者靠 `%(playlist_index)02d` 对齐，扩展名是 `wav`，与 `--audio-format wav` 一致。改这两处时要注意它们是分开的两个常量。

`_DeferredEngine` 是「一批只加载一次引擎」的实现。它长得像引擎，`generate` 转发给真引擎，`model` 与 `kwargs` 也是，所以 `verify_device` 照样能读。第一次真的用到才加载。整批没有无字幕讲次时一次都不加载。

**凭据问题与「这一讲没字幕」必须分开。** `part_transcript` 只捕获 `SubtitleUnavailable`，那是「这一讲要 ASR」。登录失效时每一讲都表现为无字幕轨，若把它也当成「这一讲要 ASR」，整门课约 39 分钟的语音识别会被跑在错误的起因上，而真正的补救动作是重新导出一次凭据。#13 为这种情况抛 `LoginRequired`，这里有意不接，让它带着下一步提示往上走。

**`asr_segments` 是纯函数，输入是文本加时间戳列表。** 它不是从模型结果里直接取分段，而是按「一单元一对毫秒」重建。这样做是为了让配对与分段逻辑可以离线测，实测用保存的原始产物秒级返回，不需要网络、不需要 GPU、不需要模型。模型只出现在 `transcribe` 的一个参数上，周围的逻辑因此也能测。

`recognised_units` 单独暴露出来，因为下标偏移是配对契约的一部分，不是内部细节。

## 下载的两处硬约束

**路径来自 `yt-dlp` 的报告，不是猜文件名。** 用的是 `--print after_move:filepath`。输出模板里有 `%(...)s` 占位符，且后处理（合并、抽音频）会改扩展名，所以磁盘上的名字无法从模板推出来。

**不强制子进程输出编码。** `yt-dlp` 按控制台代码页输出（本机是 cp936），强制 UTF-8 会把中文标题变成替换字符。这些标题会进文件名，解错了返回的路径就打不开。

### 交付文稿这一层

`transcript_text` 直接吃 `Segment` 值，不碰 `_run`，所以分隔规则可以逐条钉死。期望值来自实测数字与手读夹具。

- **`_needs_separator` / `transcript_text` 用构造的 `Segment`。** 每个方向一条断言，含汉字邻接、ASCII 邻接、数字邻接、`%` 结尾，以及真实切片两份。p12 那 55 段 608 字符一个空格都不插，p18 那 9 段 103 字符插 4 个，出 107。
- **`part_transcript` 替换 `_run`，并注入假引擎。** 替身按讲次回放有轨与无轨两种真实回包，再按 `--audio-format` 认出取音频的那一步，所以「有轨的组装成结构」「无轨的取音频并转写」都在真实字节上走。两个接缝各自独立，语音识别那侧从 `engine=` 进来。另外断言取回时交给 yt-dlp 的是 URL，见下。
- **`transcripts` 与 `transcript` 子命令替换 `_run` 与 `load_engine`，文件系统是真的。** 断言 30 讲全部落文件、21 讲 `platform` 与 9 讲 `asr` 各就各位、文件名按序、文件内容是连续正文且不含来源标记。`load_engine` 的调用次数被数下来，所以「一批加载一次」不是靠读代码相信的。

`subtitle-print-part.txt` 本来是 p18 的回包，测试里被当成「有轨」讲次的通用回包，所以那些讲次都得到 p18 的 1078 段。判定与产物的形状因此可断言，讲次之间不串味。

**跳过判定这一层有两个接缝，期望值都不来自实现。**

- `transcript_complete` 直接吃字节，接缝是文件系统。夹具是真实产物本身，不是样本：完整那份就是 `asr-23.txt` 的 51185 字节，半截那份是它前 25591 字节，切点落在字符边界上，`len(half.decode("utf-8")) == 8537` 写死在断言里，所以「解得开」这件事是被钉住的而不是被假设的。判定「完整」的那条同时钉住真实密度 4.239 与 5.418 两个端点，第 30 讲那份是按 24423 字符造的，所以下限设高了立刻失败。
- `transcripts` 里的预检替换 `_run`、注入假引擎、文件系统是真的。**跳过的证据是「没发生什么」**：取字幕与取音频的调用数是 0，引擎调用数是 0，文件时间戳不变。重跑的相反：文件内容变回 `asr-23.txt` 那 51185 字节，且取音频的调用恰好一次。这两个方向合起来才是这条 AC。
- **原子写用子进程制造真崩溃。** `AtomicWrite` 让子进程在 `os.replace` 那一步 `os._exit(7)`，所以断言的是真实的中断落在真实的位置上，而不是替换掉写入函数再观察。三条断言分别覆盖：交付名下没有文件、旧产物逐字节不变、失败的重写不破坏已有产物。实测旧实现在编码失败时会把一份 1500 字节的完成品破坏成 0 字节，这条是回归护栏。

跳过这件事的期望值来自 #17 那次真实运行的 30 份产物，不是实现重算。`delivered_text` 按实测平均密度造夹具长度，而「完整」的判据用的是实测区间，所以两边都不会跟着实现漂移。

**又漏掉一个边界，这次是参数值。** 第一版把 `Video.id` 直接放进 `part_subtitles` 的 URL 参数位，而 `Video.id` 是裸 `BV1Y5QgB5Eas`。替身不校验参数就照单全收，129 项断言全过，真实调用立刻报 `'BV1Y5QgB5Eas' is not a valid URL`。现在有一条断言直接钉住那个位置收到的值。与前面三个 bug 同一个结论：**替换掉边界之后，边界收到的值也没被验证。**

## 已知限制

**环境变量 `PYTHONIOENCODING` 会让 `probe` 崩。** 实测，与本 ticket 无关，主检出同样复现。

- 不设时，`yt-dlp` 按 cp936 写 stdout，父进程也按 cp936 解，正常。
- 设为 `utf-8` 时，`yt-dlp` 改成写 UTF-8，父进程仍按 cp936 解，于是 `_run` 抛 `UnicodeDecodeError`，`probe` 下一步拿到 `None` 再崩在 `parse_subtitle_table`。

根因是 `_run` 让平台决定编码，而 `PYTHONIOENCODING` 只影响子进程、不影响父进程的解码，两边就此不一致。修法不在本 ticket 范围内，记在这里以免下次当成新 bug 查。跑本包时不要设这个变量。

**三个曾经漏掉的 bug 说明测试的边界在哪。** 早期版本 20 项测试全过但真实调用立刻崩，因为三个问题全在 `_run` 及其返回值上，而测试把它替换掉了：`yt-dlp` 不在 PATH 上、下载返回空列表、中文路径烂掉。

现在这三条都有对应断言，但结论要记住：**替换掉边界之后，边界本身就没被验证。真实的端到端跑一次不能省。**

**清晰度是硬编码的格式编号。** 编号是站点的内部实现，会变。失效时的表现是下载报错，不是静默降级。

**1080P 高码率需要大会员。** 探测结果里能看到这一点。没有会员时拿到的是普通 1080P。

**平台字幕没有标点。** 这是已接受的取舍，不是本包的缺陷。详见「无标点是已接受的取舍」。交付文稿会是整条连续流，段落划分要靠另加策略，不在本包范围内。

**两条路径的文稿风格不同，这是已接受的取舍。** 平台字幕无标点，ASR 有标点，同一门课的交付文稿里会混着两种风格。把平台字幕也过一遍标点恢复是可行的补救路径，代价是会重算原有时间戳，本期不做。详见「平台字幕无标点，这一条落在交付文稿里」。

**不做简繁转换。** 若将来需要，正确的包名是 `opencc`。另两个同名近似的包会把「头发」错转成「頭發」，这个命名陷阱要记住。详见「不做简繁转换」。

**一次全量跑是长任务。** 实测 `BV1Y5QgB5Eas` 一次约 45 分钟，其中语音识别约 39 分钟。跑之前按后台任务安排，不要用会超时的前台命令。

**一讲失败会被记录并继续，整批跑完给出汇总。** 取不到音轨的讲次记 `failed` 加 `failure_reason = "no_audio"`；ASR 抛错的讲次记 `failed` 加 `asr_error`。两种都不写文件，都不中止整批，都不回溯已交付的讲次。跑完打印 `failed: 2 (asr_error, retryable), 7 (no_audio, not retryable)` 这样的行，名字与原因都在其中。

**两个机器级故障不算讲次失败。** 登录态失效会让每一讲都读成没字幕，缺 ASR 依赖会让每一讲都倒在引擎上。这两种各自只报一次并带出修复动作，不会变成三十条讲次失败。判据是异常类型，`LoginRequired` 与 `TranscriptionUnavailable` 直接上抛。

**ASR 分段粒度是句，不是词。** 对照过 `sentence_info` 的毫秒边界，逐段相等。词级时间戳虽然从 `timestamp` 能拿到，本包不产出。

**只做 B 站。** 其他站点未测。

**扫码超时默认 180 秒。** 超时后报「没检测到登录」，浏览器窗口会被关掉。重新跑一次即可。

## 依赖

Python 侧基础依赖只有 `websocket-client`，用于 CDP，写在 `pyproject.toml` 里。

**语音识别是可选 extra `asr`，约 2 GB，不进基础安装。** 探测、下载、字幕取回都不需要它。

```
uv sync --extra asr
```

三个包全部必需。

| 包 | 作用 |
|---|---|
| `funasr` | 引擎，提供 `AutoModel` 与三个模型 |
| `torch` | `funasr` 的张量后端 |
| `kaldi-native-fbank` | 提特征的后端 |

**第三个最容易漏。** 只装前两个时安装干净、模型也能加载，一直到送音频进去才抛错。实测 FunASR 在那种情况下的原文是

```
ImportError: torchaudio is not installed and neither is the kaldi-native-fbank fallback backend.
FunASR needs one fbank backend for feature extraction.
```

两个后端任选其一都行。本包选 `kaldi-native-fbank`，因为它不绑 torch 版本，装 `torchaudio` 则必须与所用 torch 版本匹配。

模型首次使用时从 ModelScope 下载，本机缓存在 `%USERPROFILE%\.cache\modelscope\models\iic--*`。之后靠 `disable_update=True` 跳过联网检查。

`yt-dlp` 与 `ffmpeg` 是两个外部程序，都不是 Python 包。

`yt-dlp` 优先用 PATH 上的，找不到就回退到 `uv tool run --from yt-dlp yt-dlp`。两者都没有时抛出带安装指引的错误。

`ffmpeg` 需要已经在 PATH 上。Windows 可用 `winget install Gyan.FFmpeg`。

Chrome 用于引导式登录。找不到时 `login()` 报出查过的路径，也可以显式传 `chrome=`。
