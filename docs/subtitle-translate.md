# 字幕翻译：拆块、分给多个 agent、用代码拼回来

英文 SRT 翻成中文。难点不在翻译质量，在注意力：一篇字幕几百条、上万字符，
一次生成到后段会开始丢条目、错位、漏译。所以拆成小块，每块单独翻，最后用代码拼。

## 三步

```
python scripts/srt_translate.py split <原文.srt> --out <目录> [--size 50]
# 每一块交给一个 agent 翻，产物写 <目录>/NN.zh.txt
python scripts/srt_translate.py merge <目录> --srt <原文.srt> --out <译文.srt>
```

`split` 把每一块写成 `NNNN|英文`，一行一条，编号是拼接的唯一依据。
`merge` 只读 `NN.zh.txt`，按编号取译文，时间轴和条目编号全部来自原文。

## 为什么拼要写代码

拼接的规则是确定的：编号对齐、时间轴取自原文、每行不超过 20 个汉字、最多两行。
让模型去拼等于多一次出错机会，而且错得不明显：条目少一条、时间轴错位一条，
看开头几行看不出来。代码拼完还会给出完整性报告：

```
{"cues": 623, "translated": 623, "missing": [], "missing_count": 0, "untranslated_looking": []}
```

`missing` 是缺译文的编号，`untranslated_looking` 是「译文看上去还是英文」的编号。
有 missing 时退出码为 1，不静默交付半份字幕。

## 折行不丢字

中文按 20 字折、英文按 42 字折，各自两行封顶。装不下时不是截断，是加宽重折：
连续试 20、25、30……直到两行装得下。字幕里丢半句比多出一行难发现得多。

双语版是上中下英：中文在上（最多两行），英文在下（最多两行），一条最多四行。
两个语种分别折行，行宽不同。合并时会检查中文侧与译文逐条相等，字符一个不少。

## 为什么读的是 NN.zh.txt

`NN.txt` 是原文块。拼的时候如果误读它们，会把英文当成译文拼回去，而且报告里
`translated` 照样是满的。这个坑踩过一次：第一版 `merge` 的 glob 写成
`[0-9][0-9].txt`，产物开头几行全是英文，报告却是 623/623。现在 glob 钉成
`[0-9][0-9].zh.txt`，测试里也写成译文文件名，让这个错法能被测出来。

## 给 agent 的块内指令

每条都解决一个具体的失败形态。

| 指令 | 防的是什么 |
| --- | --- |
| 行数必须与输入相等，不合并、不拆行、不跳过 | 注意力掉队时最常见的是悄悄合并相邻两条 |
| 保留 `NNNN|` 前缀 | 去掉前缀后无法对齐，只能按顺序猜 |
| 一条字幕 30 个汉字以内 | 中文比英文短，但直译容易变长，屏幕上读不完 |
| 术语表固定 | 同一部片子里 `inside fighting` 不能有三种译法 |
| 人名保留英文 | 音译各人各异，读者反而认不出 |
| 写完自查行数与编号 | 让 agent 自己先对一遍，比事后发现好 |

## 产物

`<视频名>.zh.srt`，与原文 SRT 并排放。`--bilingual` 会写成中文在上、英文在下。

## 实测

三卷，每块 50 条，块数分别是 13、12、21（共 46 个块，由 46 个 agent 并行完成）。

| 卷 | 条目 | 块数 | 合并报告 |
| --- | --- | --- | --- |
| Vol1 | 623 | 13（末块 23 条） | `623/623` |
| Vol2 | 557 | 12（末块 7 条） | `557/557` |
| Vol3 | 1032 | 21（末块 32 条） | 见下 |

三份产物都做了对齐检查：条目数与原文相等，时间轴逐条相同（差 0 处），
没有一条译文还是英文。中文长度中位数 10 到 12 字，最长 32 字。
